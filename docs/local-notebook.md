# PassBy 2.0：只在本机的密码本（改造计划）

状态：草案，2026-11-14。等创始人看过计划和原型后确认，确认前不动产品代码。依据 Tenon-AI `docs/ideas.md` 的 I2、I3（产品组 11-14 转达）。

一句话：PassBy 回到一个纸质密码本的样子。密码只存在这台手机上：没有账号，不联网，没有服务器。打开以后验证一次 Face ID 就是列表，点一条就复制。备份和换手机靠两样：系统迁移和加密导出文件。

## 1. 现状和数据

- **使用量**：服务器 11-14 读到的数据（只读）。近 30 天还有效的 PassBy 登录只有 2 个 Tenon 身份。iPhone 会话 4 个，每个都带续期凭据，大致对应 4 台设备次；网页会话 5 个，都属于同一人。没有人用过产品删除。App Store 评分数为 0。
- **待补**：付费单位数、近 30 天活跃设备数、各版本占比，要从 App Store Connect 读。创始人的 Connect 登录已经过期，等他重新登录（待办 Q109）后由总办代查，拿到后补在这里；在那之前不填估计值。
- **现在的本机存储**：
  - 整本（条目、分组、最近删除、未保存的草稿）用 AES-256-GCM 加密，存在 `Application Support/PassBy/<所有者>/notebook.passby`。
  - 密钥就是恢复密钥，存在钥匙串里，属性是「仅本机、需设备密码、绑定当前 Face ID」。Face ID 重新录入后，这把密钥就失效。
  - 文件不进系统备份。
  - iCloud 私有库里存同一本密文；网页版读的就是这一份。
- **旧版在账号失效后**：按代码，已有本机密码本的旧版仍能用 Face ID 打开，只是不能同步。下线前在真机上验证。

## 2. 新版做什么

| | |
| --- | --- |
| 去掉 | Tenon 登录、iCloud 同步、恢复密钥、网页版、认证服务、统一删除协议、录屏时拒绝解锁 |
| 保留 | 条目（标题、账号、密码、备注）、分组、搜索、密码生成器、最近删除（30 天）、复制后 60 秒过期、切到后台时遮住界面 |
| 新增 | 加密导出和导入、上次导出日期和提醒、笔记本外观、安卓版 |

闭环是这几步：记下、找到、复制、备份（导出）、换手机（导入或系统迁移）。

## 3. 打开和门禁

- **冷启动**：Face ID 开着时，系统验证一次就进列表；关着时直接进列表。默认开着，在设置里可以关。
- **切回前台**：离开不满 5 分钟，不再验证；满 5 分钟要验证一次。离开的瞬间界面就被遮住，所以多任务界面的缩略图里看不到密码。
- **没有 Face ID 的机型**：用 Touch ID。两样都没有，就用设备密码（`deviceOwnerAuthentication`）。
- **录屏和镜像**：不再拒绝解锁，只把明文密码显示成圆点，复制照常。
- **Face ID 重新录入**：新版的数据不靠绑定 Face ID 的密钥（见下一节），所以重新录入不影响打开。

## 4. 本机存储

- **形式**：一个 JSON 文件，由 iOS 的文件级加密保护（`NSFileProtectionComplete`，手机锁着时谁都读不了），不再另加 App 自己的密钥。
  - 原因：App 自己的密钥如果放在「仅本机」的钥匙串里，系统迁移后新手机会得到一个打不开的密码本。
  - 这样做，安全的责任交给手机：锁屏密码，加上 Face ID 这道门。
- **备份**：文件不再排除在系统备份之外，跟着 iCloud 云备份、电脑加密备份和「快速开始」换机走。
- **iCloud 云备份的风险**：用户没开「高级数据保护」时，Apple 能读取 iCloud 备份的内容。App 内的说明照实写，建议开启高级数据保护，或者改用电脑加密备份。
- **写入**：每次改动立即原子写入，同时保留上一份（`.previous`），写坏时可以回退。
- **要在真机上验证的换机方式**，结果写进文档和 App 内说明：
  - 「快速开始」两台 iPhone 直接传输；
  - 从 iCloud 云备份恢复，分开过和没开过高级数据保护两种；
  - Mac 或 PC 的加密备份；
  - 不加密的电脑备份。按文件级加密的规则，这种预计带不过去。

## 5. 老用户迁移（验收重点）

升级到 2.0 后第一次打开，按顺序做：

1. **解开旧文件**：用 Face ID 读旧密钥，解开本机旧文件。
   - 如果密钥已经失效（Face ID 改过），请用户输入恢复密钥。恢复密钥就是这把密钥，能直接解开本机文件。
   - 本机没有文件（例如重装过），就用恢复密钥解 iCloud 里的那份。
2. **读一次 iCloud（建议做，待创始人定）**：只读，取 iCloud 里那份密文，和本机的合并。
   - 原因：在网页或另一台设备上的改动，可能还没同步到这台手机。
   - 合并沿用现在的规则：同一条两边都改过，两份都留。
   - 迁移完成后，这台手机就不再调用 iCloud。
3. **核对后才切换**：条目数、分组数、最近删除数和旧数据完全一致才写新文件。不一致就停下来，保留旧数据并提示，不做任何删除。
4. **完成页**：显示迁移了多少条，然后交给用户选。
   - 立即导出一份。
   - 删除 iCloud 里的旧密文：可以在 App 里点一下（删一次），也可以去「设置 › Apple 账户 › iCloud › 管理存储空间」里删。
5. **收尾**：用户确认以后，删掉本机旧密文和钥匙串里的旧密钥。

有两台设备的用户，两台各自迁移，之后各自独立，App 内会说明这一点。

**联网问题**：2.0 里的 iCloud 代码只在第 1–2 步用到。新装的 2.0，以及迁移完成后的 2.0，都不发任何网络请求，抓包验收就按这两种情况做。网页版下线、旧版本基本升级完以后，2.1 删掉 iCloud 的代码和权限，从那以后无条件不联网。

## 6. 加密导出和导入

**库**：都用 libsodium 1.0.22。

| 平台 | 封装 | 版本 | 许可 |
| --- | --- | --- | --- |
| iOS | swift-sodium（libsodium 作者维护） | 0.11.0，2026-05 | ISC |
| 安卓 | kotlin-multiplatform-libsodium | 0.9.6，2026-11 | Apache-2.0 |

备选的 lazysodium-android 5.2.0 最后一次更新是 2025-05，维护较慢。几个许可都允许商用，关于页列出第三方许可。

**算法**：
- 口令经 Argon2id（v1.3）派生出 256 位密钥：`opslimit=3`，`memlimit=64 MiB`，并行度 1。这是 RFC 9106 的第二推荐参数，老手机上大约 1 秒。
- 用 XChaCha20-Poly1305（IETF）加密并校验。
- 每次导出用新的 16 字节盐和 24 字节随机数。

**文件**：`PassBy-年-月-日.passby`，二进制，大端序。

| 字节 | 内容 |
| --- | --- |
| 0–7 | ASCII `PASSBYEX` |
| 8 | 格式版本 `1` |
| 9 | 派生算法 `1` = Argon2id v1.3 |
| 10–13 | `opslimit`（uint32） |
| 14–17 | `memlimit`，单位 KiB（uint32） |
| 18–33 | 盐，16 字节 |
| 34–57 | 随机数，24 字节 |
| 58–73 | 口令校验值：派生出的密钥对固定串 `PassBy export key check` 做带密钥的 BLAKE2b，取前 16 字节 |
| 74– | 密文加 16 字节认证标签。附加数据是第 0–73 字节，所以文件头也受保护 |

**明文**：UTF-8 JSON，内容是 `{"format":1,"exportedAt":…,"folders":[…],"entries":[…]}`，和本机文件的字段一致。最近删除不导出。

**导出码和口令**：
- 默认由 App 生成 20 位 Crockford Base32 字符（不含 I、L、O、U），约 100 位随机性，显示成 4 组，每组 5 位。新手机可以手动输入，也可以扫旧手机屏幕上的二维码。输入不分大小写，I/L 当作 1，O 当作 0。
- 用户也可以自己设口令，至少 10 位，界面显示强弱。
- 导出码和口令都不保存。

**报错要分得开**：
- 校验值对不上：「导出码或口令不对」。
- 校验值对、但认证失败：「文件已损坏或被改动」。
- 格式版本或参数不认识：「请更新 PassBy」。
- 只靠认证失败，分不出口令错和文件被改；所以加了校验值。它只能用来验口令，不比密文本身泄露得多。

**导入**：
- 本机是空的，就直接导入。
- 本机不空，默认合并：同一条且内容相同的跳过，内容不同的两份都留，旧的标「（导入）」。也可以选择替换。
- 导入前显示文件里的条数。

**兼容**：iPhone 和安卓共用同一份格式文档和测试向量（固定口令、盐和随机数对应固定输出），两端都要通过。格式文档放到支持页。

**不做**：明文导出。从浏览器或其他密码管理器导入 CSV 放到后面的版本，导入后提醒删除原文件。

**提醒导出**：设置页显示上次导出日期。从来没导出过，或者超过 30 天没导出、期间又有改动，就在列表顶部提示一次，可以关掉。

## 7. 界面

可点的原型见第 14 节。

- **纸张**：米黄色，浅蓝横线，左侧一条红色页边线。深色外观用深棕纸张配浅色字，符合产品规范 4.3。
- **字体**：
  - 标题和名称用手写体霞鹜文楷 Lite（OFL 1.1，约 14 MB，中英文都有，App 会因此从 3.6 MB 变大到约 18 MB）。
  - 密码用 JetBrains Mono（OFL 1.1）。0 带点，和 O 分得开；1、l、I 字形各不相同。
  - 正文和按钮用系统字体，保证小字号也看得清。
  - 原型里可以切换另外两种手写体比较。
- **取用**：
  - 打开就是列表，搜索框在顶部。
  - 点一行就复制密码，底部提示「已复制，60 秒后清除」。
  - 行尾的「›」进详情，详情里可以看、编辑、复制账号。
  - 不做翻页之类的动画。
- **可访问性**：支持动态字体、旁白读屏、深浅色、减少动态效果。手写体在最大字号下保持可读；超出时换成系统字体。

## 8. 安卓

**建议两端都用原生**：iPhone 保留现在的 SwiftUI，安卓用 Kotlin 和 Jetpack Compose。两端共用格式文档和测试向量。理由如下：

- App 小，只有五六个页面。真正的工作量在平台相关的部分：生物识别、文件级加密、备份、剪贴板、遮挡界面、不联网的权限声明。跨端框架在这些地方都要写原生桥接，省不了多少。
- iPhone 版已经在线上。换成 Flutter 或 React Native 等于重写，迁移风险也落到老用户身上。
- Kotlin Multiplatform 可以共享格式和加密的代码。但这部分本来就很小（解析文件头再调 libsodium），用测试向量保证两端一致更简单。

**安卓的要点**：
- minSdk 26，生物识别用 `androidx.biometric`，没有生物识别时退回设备凭据。
- 数据放在 App 私有目录，由系统的文件级加密保护。
- 跟着系统自动备份和设备间迁移走。设了锁屏的设备，自动备份是端到端加密的，要在真机上验证。
- `FLAG_SECURE`：不能截屏，多任务界面不显示内容。
- 剪贴板：带敏感标记（`EXTRA_IS_SENSITIVE`），60 秒后清除。
- 清单里不声明 `INTERNET` 权限，并检查合并进来的依赖没有加上它。

**工作量**：开发会话约 8–12 个工作日，含界面、迁移不涉及的部分、真机测试和上架资料。签名密钥由安全组保管。

**渠道**：渠道定之前不发布（I3）。是否另开安卓开发会话，等创始人看完原型后，由我告诉产品组。

## 14. 原型

可点的界面原型：https://claude.ai/artifact/HG9SJ6zcR2pitC6JSghTCE，浅色和深色两张，都能点。

- **怎么用**：在画布上点任一张的播放按钮。「调整」里能切三样：手写体（霞鹜文楷、龙藏体、马善政）、开始画面（日常打开、老用户升级、Face ID 关闭）、深色。
- **能走通的流程**：
  - 解锁；
  - 点一行复制；
  - 搜索和分组；
  - 查看、编辑、新建，含生成密码；
  - 删除和恢复；
  - 导出（导出码和二维码，或者自己设口令），然后分享；
  - 导入，包括口令错和文件被改动两种报错；
  - 设置，含 Face ID 开关；
  - 老用户搬迁；
  - 删除 iCloud 旧密文；
  - 换手机说明。
- **原型里的替代**：
  - 原型里的字体是霞鹜文楷的繁体版（Google Fonts 上的 TC 版），App 里用简体的 Lite 版。
  - 二维码只是示意图案，扫不出内容。
  - 分享面板是模拟的。
  - 数据都是虚构的。
