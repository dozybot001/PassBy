## 2. 新版做什么

| | |
| --- | --- |
| 去掉 | Tenon 登录、iCloud 同步、恢复密钥、认证服务、统一删除协议、录屏时拒绝解锁。网页版保留，改成手机那本的只读副本（第 9 节） |

闭环是这几步：记下、找到、复制、备份（导出）、换手机（导入或系统迁移）。

## 3. 打开和门禁

- **冷启动**：Face ID 开着时，系统验证一次就进列表；关着时直接进列表。默认开着，在设置里可以关。
- **切回前台**：离开不满 5 分钟，不再验证；满 5 分钟要验证一次。离开的瞬间界面就被遮住，所以多任务界面的缩略图里看不到密码。
- **没有 Face ID 的机型**：用 Touch ID。两样都没有，就用设备密码（`deviceOwnerAuthentication`）。
- **手机没有设锁屏**（11-14 和安卓会话对齐，两端一样）：不拦，直接进列表。第一次打开提示一次：没有锁屏时，手机的文件加密起不到保护作用，建议设锁屏密码；设置里门禁开关旁写明「这台手机没有设锁屏」。
- **录屏和镜像**：不再拒绝解锁，只把明文密码显示成圆点，复制照常。
- **Face ID 重新录入**：新版的数据不靠绑定 Face ID 的密钥（见下一节），所以重新录入不影响打开。

## 4. 本机存储

- **形式**：一个 JSON 文件，由 iOS 的文件级加密保护（`NSFileProtectionComplete`，手机锁着时谁都读不了），不再另加 App 自己的密钥。
  - 原因：App 自己的密钥如果放在「仅本机」的钥匙串里，系统迁移后新手机会得到一个打不开的密码本。
  - 这样做，安全的责任交给手机：锁屏密码，加上 Face ID 这道门。
- **备份**：文件不再排除在系统备份之外，跟着 iCloud 云备份、电脑加密备份和「快速开始」换机走。
- **不加 App 密钥的代价**，App 内说明和隐私政策都照实写：
  - iCloud 云备份：用户没开「高级数据保护」时，Apple 能读取备份内容。建议开启高级数据保护，或者改用电脑加密备份。
  - 不加密的电脑备份：按 Apple 平台安全文档，备份不加密时，文件不论数据保护等级都不加密（钥匙串除外）。所以密码本很可能以明文留在电脑的备份里。要在真机上验证；属实的话，建议在 Mac「访达」或 iTunes 里勾选「加密本地备份」。
- **内容**：条目、分组、最近删除（30 天）和上次导出日期都在这一个文件里，不放 UserDefaults。
- **写入**：每次改动立即原子写入，同时保留上一份（`.previous`），写坏时可以回退。
- **要在真机上验证的换机方式**，结果写进文档和 App 内说明：
  - 「快速开始」两台 iPhone 直接传输；
  - 从 iCloud 云备份恢复，分开过和没开过高级数据保护两种；
  - Mac 或 PC 的加密备份；
  - 不加密的电脑备份：看能不能带过去，也看电脑上的备份里是不是明文。

## 5. 迁移

改免费以后可能有新用户（产品组 11-14），迁移代码按通用的做，对所有本机有旧文件的设备都一样：

1. **升级前**在旧版里打开一次，让网页上的改动同步到手机。
2. **升级后第一次打开**：用 Face ID 读旧密钥，解开本机旧文件；密钥已经失效（Face ID 改过）时输入恢复密钥。
3. **核对后才切换**：旧数据的每一条条目、每个分组、每条最近删除都在新文件里，且内容一致，才切换。不满足就停下来提示原因，保留旧数据，不删任何东西，也不显示空本子。
4. **完成页**：显示「原有 N 条全部搬入」，提供立即导出一份。
5. **旧密文和旧密钥一直留着**：迁移时不删，以后也不自动删（见开头的硬约束）。

**每个旧目录都迁**（产品组 11-14 复核）：
- 旧文件在 `Application Support/PassBy/<目录>/notebook.passby`。目录名是 iCloud 用户记录 ID 的哈希，钥匙串里对应的账号是 `aes-gcm-key-v1-<目录名>`；早期还可能有 `local` 目录。
- 逐个目录找，不靠登录信息定位，每个有旧文件的目录都迁，不只迁第一个。
- 几本合进 2.0 的一本：同一条且内容相同的只留一份，内容不同的都留下。核对按每本分别对：每本的每一条都在。
- 未保存的草稿（`LocalVaultState.draft`）也是数据：搬成一条单独的条目，标题后加「（未保存的草稿）」，完成页列出来。

**App 转到公司的开发者账号**：转账号后 Team ID 前缀会变。按 Apple 的转让说明，旧钥匙串里的密钥会读不到，那之后迁移只能靠恢复密钥。所以转账号要排在创始人的设备都迁完之后，转之前再按 Apple 当时的说明核实一次。

2.0 不带 iCloud 代码和权限，从第一版起就不联网，抓包验收按这个做。去掉 iCloud 代码不会删 iCloud 里的数据：旧密文留在创始人自己的 iCloud 里，App 不提示删；以后要读，用恢复密钥加一个带 iCloud 权限的版本或网页令牌就能读回来。

## 6. 加密导出和导入

**只用系统自带的加密**（法务组 11-14 的出口合规意见，Tenon-AI 4011a90）：用 libsodium 这类不是系统提供的加密，在法国上架要先交法国的加密申报，可能卡送审几周。只用 Apple 系统里的加密，出口合规照 1.x 答，`ITSAppUsesNonExemptEncryption` 保持 `NO`，不用交文件。这样也不带任何第三方库，关于页不用列三方许可。

| 平台 | 口令派生 | 分子密钥 | 加密 |
| --- | --- | --- | --- |
| iOS | CommonCrypto `CCKeyDerivationPBKDF`（PBKDF2-HMAC-SHA256） | CryptoKit `HKDF<SHA256>` | CryptoKit `AES.GCM` |
| 安卓 | 用 `Mac`（`HmacSHA256`）照 RFC 8018 算 PBKDF2，不用 `PBEKeySpec` | 用 `Mac`（`HmacSHA256`）照 RFC 5869 写 HKDF，十来行 | `Cipher` 的 `AES/GCM/NoPadding` |

**格式**：文件布局、口令进 PBKDF2 前的字节、密钥派生、明文 JSON 和导入的检查顺序，都写在 `docs/export-format.md`。要点：
- PBKDF2-HMAC-SHA256 迭代 600,000 次得到主密钥，HKDF-SHA256 分出加密和校验两把子密钥，AES-256-GCM 加密，文件头作附加数据。导入时迭代次数限在 100,000–10,000,000。
- 不用 Argon2id 的代价：用户自己设的口令，抗显卡暴力破解要弱一些。默认的导出码约 100 位随机性，不受影响。所以自设口令至少 12 个字符，并建议用导出码。
- 最近删除不导出。

**导出码和口令**：
- 默认由 App 生成 20 位导出码（约 100 位随机性），显示成 4 组，每组 5 位，旁边显示二维码。导入时手动输入或粘贴；App 里不做扫码，相机 App 能读二维码里的文字再复制粘贴（11-14 和安卓会话对齐：免得安卓为扫码带 ZXing 和 CameraX、申请相机权限）。
- 用户也可以自己设口令，界面显示强弱。
- 导出码和口令都不保存。

**报错要分得开**：口令错报「导出码或口令不对」，文件被改报「文件已损坏或被改动」，版本不认识报「请更新 PassBy」。只靠 AES-GCM 认证分不出前两种，所以加了口令校验值；它只能用来验口令，不比密文本身泄露得多。

**导入**：
- 本机是空的就直接导入；不空就默认合并，也可以选替换。细则写在 `docs/export-format.md` 第 7 节，iPhone 和安卓照同一套做。

**兼容**：iPhone、安卓和网页共用同一份格式文档和测试向量（固定口令、盐和随机数对应固定输出），三端都要通过。格式文档 `docs/export-format.md`，测试向量 `docs/export-vectors.json`，参考实现 `scripts/export-format.mjs`（11-14 写好，CryptoKit 和 WebCrypto 都解开了全部有效向量）；公开后放到支持页。

**不做**：明文导出。从浏览器或其他密码管理器导入 CSV 放到后面的版本，导入后提醒删除原文件。

**提醒导出**：设置页显示上次导出日期。从来没导出过，或者超过 30 天没导出、期间又有改动，就在列表顶部提示一次，可以关掉。

## 8. 安卓

**建议两端都用原生**：iPhone 保留现在的 SwiftUI，安卓用 Kotlin 和 Jetpack Compose。两端共用格式文档和测试向量。理由如下：

- App 小，只有五六个页面。真正的工作量在平台相关的部分：生物识别、文件级加密、备份、剪贴板、遮挡界面、不联网的权限声明。跨端框架在这些地方都要写原生桥接，省不了多少。
- iPhone 版已经在线上。换成 Flutter 或 React Native 等于重写，迁移风险也落到老用户身上。
- Kotlin Multiplatform 可以共享格式和加密的代码。但这部分本来就很小（解析文件头再调系统加密），用测试向量保证两端一致更简单。

**安卓的要点**：
- minSdk 26，生物识别用 `androidx.biometric`，没有生物识别时退回设备凭据。
- 数据放在 App 私有目录，由系统的文件级加密保护。
- 跟着系统自动备份和设备间迁移走。设了锁屏的设备，自动备份是端到端加密的，要在真机上验证。
- `FLAG_SECURE`：不能截屏，多任务界面不显示内容。
- 剪贴板：带敏感标记（`EXTRA_IS_SENSITIVE`），60 秒后清除。
- 清单里不声明 `INTERNET` 权限，并检查合并进来的依赖没有加上它。

**工作量**：开发会话约 8–12 个工作日，含界面、迁移不涉及的部分、真机测试和上架资料。签名密钥由安全组保管。

**渠道**：创始人 11-14 定免费，先放 Gitee 和 GitHub 的 Releases，不等 Google Play（Q114）。法务组核实：真的不联网，国内直接分发安装包不用 App 备案。放安装包要等仓库公开；第一次放出来之前，安卓会话请创始人确认一次。

**签名和发布**：照产品规范 15.6，在 Releases 发布照 15.6.7（安全组 11-14）：签完用 `apksigner verify --print-certs` 核对证书指纹，不一致就停；每个版本在 Release 说明里写安装包的 SHA-256 并附 `SHA256SUMS`；Gitee 和 GitHub 传同一个文件，传完两边各下载一次核对；证书的 SHA-256 指纹固定写在支持页上；安装说明写明更新时提示签名不一致、要先卸载的就不要装，先到支持页核对。

**法律文本**：法务组 11-14 出了安卓版的隐私政策和用户协议文字（存在 `docs/legal-2.0-draft.md` 末尾），和安卓版同一天加在当时现行的版本上，PassBy 改页面；支持页加「核对安卓安装包」和证书指纹。安卓可能比 iPhone 2.0 先发。

**谁来做**：产品组另开「PassBy 安卓 · 开发」会话，和 PassBy 并行，工作目录同在 `~/PassBy`，只动 `android/` 和 `docs/android.md`。导出格式文档和测试向量归 PassBy，它照着实现。两个会话在同一个工作目录里提交，各自只提交自己的路径（`git commit -- <路径>`），不用 `git add -A` 或 `commit -a`。

## 9. 新网页版，和认证服务下线

**新网页版**（产品组方案，创始人 11-14 19:03 定「按方案做」）：
- **手机那本的只读副本**：查看、搜索、复制。新建、修改、删除只在手机上做，没有密码生成器。页面顶部写明这份副本是哪天导出的。
- **不登录，没有服务端接口**：静态页面。把手机导出的 `.passby` 文件拖进页面，输入导出码或口令，解密和显示都在浏览器里。格式和口令字节照第 6 节；PBKDF2、HKDF、AES-GCM 都用浏览器自带的 WebCrypto，不带加密库。
- **默认不存**：打开「这是我自己的电脑」才把密文存进浏览器，用这台电脑的指纹或开机密码解锁：建一个本站的通行密钥，用它的 PRF 扩展取一把钥匙，每次打开验证一次。通行密钥会随 Apple「密码」或 Google 密码管理器同步到用户的其他设备，所以界面和隐私政策不写「钥匙只在这台电脑上」。不支持 PRF 的浏览器不提供记住，每次重新选文件、输导出码。离开窗口或 5 分钟不动就锁上，内存里的明文清掉。设置里有「从这台电脑删除」。
- **页面不向任何地方发数据**：内容安全策略 `connect-src 'none'`，不带第三方脚本和统计；照旧不缓存、不用 service worker。通行密钥的调用不受 `connect-src` 管，也不经过我们的服务器。
- **可行性**（PassBy 11-14 核对）：
  - PBKDF2-SHA256 60 万次：Chrome 156（Apple M5 Pro）约 37 毫秒，Node 约 43 毫秒。老电脑慢 10–20 倍也在 1 秒内，不用改迭代次数。Safari、Firefox 和 Windows 上的耗时等做出来再量。
  - PRF：Chrome 156 的 `getClientCapabilities()` 报 `extension:prf` 为真。按第三方资料（未经官方核实），Safari 18 起配 Apple「密码」可用，但不支持外接安全钥匙；Chrome 和 Edge 配 Google 密码管理器可用；Windows Hello 要 2026 年 2 月以后的更新；Firefox 各说法不一。所以不按浏览器列名单，运行时判断：先看 `getClientCapabilities()`，建通行密钥时看 `prf.enabled`，第一次验证真拿到钥匙才打开「记住」。哪一步不行就退回每次选文件。
  - 风险：通行密钥被删、换了密码管理器，存在浏览器里的副本就打不开了。它只是副本，提示重新导入就行，不会丢数据。
- **安全组的要求**（11-14，Tenon-AI `docs/setup/tenonai-cn-security.md`「PassBy 2.0」，eb830b0）：
  - 通行密钥：不写 `rp.id`，默认就是 passby.tenonai.cn，不能写成 tenonai.cn。创建和每次取钥匙都用 `userVerification: 'required'`。用户名用固定的「PassBy」。
  - 存法：PRF 输出经 HKDF（info `PassBy web v1 local`）派生一把不可导出的 AES-GCM 钥匙，用新随机数加密解开后的 JSON。IndexedDB 里只存凭据 ID、PRF 盐、随机数、密文和导出日期。不存导出码、主密钥和 PRF 输出，不写 localStorage；重新导入就整份替换。不支持 PRF 就退回每次选文件，不把钥匙直接存进浏览器。
  - 「从这台电脑删除」：删 IndexedDB 里的记录。浏览器有 `PublicKeyCredential.signalUnknownCredential` 就顺带调用，让密码管理器删掉这把通行密钥；没有就提示去系统设置里删。
  - 解开的条目当作不可信内容：只用 `textContent` 和 `replaceChildren()`，不用 `innerHTML`；网址只放行 http 和 https，链接加 `rel="noopener noreferrer"`。
  - 第一次打开时删掉旧网页版在这个源上留下的数据：IndexedDB 的 `passby-trusted-browser`，以及 localStorage 里登录相关的键；语言偏好可以留。新网页版要等创始人确认、旧网页版撤掉以后才上线（见下面的上线顺序），所以这时删已经不违反硬约束。
  - 这个源上只放新网页版和隐私、支持、条款页；旧网页版的 CloudKit 脚本和 `/auth/redirect/` 都撤掉，因为同源页面能读同一个 IndexedDB。
  - 响应头改 `passby.caddy` 的 header 块，整站生效：`Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; manifest-src 'self'; connect-src 'none'; form-action 'none'; frame-ancestors 'none'; base-uri 'none'; object-src 'none'; require-trusted-types-for 'script'`；`Cross-Origin-Opener-Policy` 改成 `same-origin`；其余照旧。不发 `Clear-Site-Data`，免得删掉用户存下的副本。
  - 上线前安全组验收：查响应头；读线上 JS（rp、userVerification，有没有 fetch、XHR、WebSocket、sendBeacon 和外部地址）；在浏览器里走一遍打开、导入、解锁、复制、锁定，确认没有网络请求，也没有 CSP 报错。
- **旧网页版先加「导出为 .passby」**（产品组 11-14 建议，PassBy 同意）：2.0 送审前，在现在的网页版加一个导出：读 iCloud 里的密码本，在浏览器里按第 6 节的格式加密，下载成文件。创始人升级前就有一份独立的备份；改免费以后要是有外部用户，这也是他们的取回办法。约 1 个工作日。
