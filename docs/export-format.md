# PassBy 导出文件格式（第 1 版）

iPhone、安卓和网页三端共用这份格式。三端都要通过 `docs/export-vectors.json` 里的全部测试向量。参考实现是 `scripts/export-format.mjs`：

- `node scripts/export-format.mjs`：重新生成测试向量，并逐条核对。
- `node scripts/export-format.mjs --check`：只核对仓库里现有的测试向量。

11-14 另用 CommonCrypto 加 CryptoKit（iOS 的做法）和 WebCrypto（网页的做法）各自解开了全部有效向量。

只用各平台系统自带的加密（PBKDF2、HKDF、HMAC、AES-GCM），不带第三方库。原因见 `docs/local-notebook.md` 第 6 节。

## 1. 文件

- 文件名：`PassBy-年-月-日.passby`。
- 文件是二进制，整数一律大端序。
- 前 58 字节是文件头，后面是密文，最后 16 字节是认证标签。

| 字节 | 内容 |
| --- | --- |
| 0–7 | ASCII `PASSBYEX` |
| 8 | 格式版本，现在是 `1` |
| 9 | 派生算法，`1` = PBKDF2-HMAC-SHA256 |
| 10–13 | 迭代次数（uint32）。导出时用 600,000 |
| 14–29 | 盐，16 字节，每次导出都用系统随机数新生成 |
| 30–41 | AES-GCM 随机数，12 字节，每次导出都新生成 |
| 42–57 | 口令校验值，16 字节（第 3 节） |
| 58 到倒数第 17 字节 | 密文 |
| 最后 16 字节 | AES-GCM 认证标签 |

附加数据（AAD）是第 0–57 字节，所以改动文件头也会被发现。

## 2. 口令进 PBKDF2 之前的字节

导入时，用户输入的可能是导出码，也可能是自己设的口令，按下面的顺序判断。

### 2.1 导出码

1. 去掉下面两类字符：
   - 空白：U+0009–U+000D、U+0020、U+0085、U+00A0、U+1680、U+2000–U+200A、U+2028、U+2029、U+202F、U+205F、U+3000、U+FEFF；
   - 横线：U+002D、U+2010–U+2015。
2. ASCII 小写字母转大写。
3. `I`、`L` 换成 `1`，`O` 换成 `0`。
4. 结果正好是 20 个字符，并且每个都在 `0123456789ABCDEFGHJKMNPQRSTVWXYZ`（Crockford Base32，不含 I、L、O、U）里，就是导出码。

导出码的字节就是这 20 个字符的 ASCII 字节。

不满足第 4 步，就按自设口令处理。

### 2.2 自设口令

1. 去掉首尾的空白，空白的范围同 2.1；中间的空白保留。
2. 做 Unicode NFC 规范化。
3. 取 UTF-8 字节。

安卓不要用 `PBEKeySpec`：它收 `char[]`，转成字节的方式随实现而定。照上面三步得到字节，再自己用 `Mac`（`HmacSHA256`）按 RFC 8018 算 PBKDF2。

### 2.3 导出时设口令的规则

导出时设口令，要过下面三条：

- 首尾不能有空白（空白的范围同 2.1）。
- 不能看起来像导出码，即按 2.1 的步骤得出合法的导出码。这样导入时不会把它误当成导出码。
- 至少 12 个字符：NFC 规范化后的 Unicode 码位数，一个表情算一个，一个汉字算一个。

### 2.4 生成导出码

- 用系统的安全随机数，取 20 个字符，每个从 Crockford 字母表里均匀选（每个 5 位，共 100 位）。
- 显示成 4 组、每组 5 位，用 `-` 隔开，例如 `7K3M9-Q2XHB-R8T4V-W6YZ0`。
- 二维码里放的也是这串带横线的文字。

## 3. 密钥

```
master   = PBKDF2-HMAC-SHA256(口令字节, 盐, 迭代次数, 32 字节)
encrypt  = HKDF-SHA256(IKM = master, salt = 空, info = "PassBy export v1 encrypt", 32 字节)
checkKey = HKDF-SHA256(IKM = master, salt = 空, info = "PassBy export v1 check",   32 字节)
check    = HMAC-SHA256(checkKey, ASCII "PassBy export key check") 的前 16 字节
```

- HKDF 照 RFC 5869。salt 为空，即长度为 0，按 RFC 等同于 32 个零字节。
- info 是 ASCII 字节。
- 加密用 AES-256-GCM：密钥 `encrypt`，随机数取文件头第 30–41 字节，附加数据取文件头第 0–57 字节，标签 16 字节。

## 4. 明文

明文是 UTF-8 编码的 JSON。

```json
{
  "format": 1,
  "exportedAt": "2026-11-14T12:00:00Z",
  "folders": [{ "id": "6F1C2A4E-8B3D-4C5E-9F60-1A2B3C4D5E6F", "name": "工作" }],
  "entries": [{
    "id": "0E8F6A2B-1C3D-4E5F-8A9B-0C1D2E3F4A5B",
    "title": "个人邮箱", "account": "alex@example.com", "password": "…", "notes": "…",
    "folderID": "6F1C2A4E-8B3D-4C5E-9F60-1A2B3C4D5E6F"
  }]
}
```

字段规则：

- `format` 是整数，现在是 `1`。比它大的，提示「请更新 PassBy」。
- `exportedAt` 是导出时刻，UTC，ISO 8601，精确到秒。网页版在页面顶部显示它。
- `id` 和 `folderID` 是 UUID。导出时用大写；导入时大小写都认。
- `title`、`account`、`password`、`notes` 都是字符串，可以为空，内容原样保留，不做规范化。
- `folderID` 可以没有，表示未分组。有的话，必须指向 `folders` 里的一个分组。
- 分组的 `id` 不能重复，条目的 `id` 也不能重复。
- 最近删除不导出。
- 不认识的字段，导入时忽略。

## 5. 导入的检查顺序和报错

| 顺序 | 检查 | 不通过时 | 提示 |
| --- | --- | --- | --- |
| 1 | 文件至少 74 字节，开头是 `PASSBYEX` | `notExport` | 这不是 PassBy 的导出文件 |
| 2 | 格式版本和派生算法都是 `1` | `update` | 请更新 PassBy |
| 3 | 迭代次数在 100,000–10,000,000 | `damaged` | 文件已损坏或被改动 |
| 4 | 算出的校验值等于文件头里的（常数时间比较） | `wrongCode` | 导出码或口令不对 |
| 5 | AES-GCM 解密、认证通过 | `damaged` | 文件已损坏或被改动 |
| 6 | JSON 能解析，`format` 是整数 | `damaged` | 同上 |
| 7 | `format` 是 `1` | `update` | 请更新 PassBy |
| 8 | 字段符合第 4 节 | `damaged` | 文件已损坏或被改动 |

第 3 步放在派生之前，免得恶意文件用很大的迭代次数把设备拖住。

改了盐的文件会在第 4 步报 `wrongCode`：盐参与派生，算不出同一个校验值。这一种分不出来，可以接受。

## 6. 测试向量

`docs/export-vectors.json` 有三组。

- **`valid`**：五个能解开的文件。
  - 每个文件给出：输入的原文、等价输入、口令字节、各把密钥、校验值、明文、整个文件（Base64）。
  - 五个文件覆盖：导出码（含小写、I/L/O、空格的写法）、首尾带空格的中文口令、带表情（代理对）的口令、按 NFD 输入的带组合符号的口令。
  - 每个实现都要做到两点：用 `typed` 和每个 `equivalentInputs` 解开文件，得到 `plaintext`；用给定的盐和随机数，加密出逐字节相同的文件。
- **`invalid`**：十个解不开的文件。实现要报出 `error` 列的那一类错误。
- **`passphraseRules`**：设口令的规则（第 2.3 节）。实现要给出相同的结论。

## 7. 导入合并（iPhone 和安卓一致）

网页版是只读副本，每次导入整份替换，不合并。手机上导入，本机是空的就直接导入；本机不空，默认合并，也可以选替换。

**合并**：
- 分组：
  - `id` 相同（不分大小写）的算同一个分组，名称以本机为准。
  - `id` 不同但名称相同（NFC 后逐字相同）的，并进本机那个分组，文件里指向它的条目改指本机的分组。
  - 其余分组照文件加进来。
- 条目：
  - 按 `id` 找本机的同一条，不分大小写，只和本机现有的条目比，不和最近删除里的比。
  - 找到了，再比标题、账号、密码、备注、分组五项，分组按上一条换算后的 `id` 比。五项都相同就跳过；有不同，本机那条不动，文件里那条换一个新 `id` 加进来，标题后加「（导入）」，英文界面加「 (Imported)」。
  - 找不到，照文件加进来。要是这个 `id` 正好和最近删除里的某条相同，换一个新 `id`，标题不加标记，免得以后恢复时撞上。
- 最近删除和草稿不受影响。

**替换**：分组换成文件里的；本机原有的条目全部进最近删除，留 30 天，不带分组；文件里的条目照原样加进来。

导入前显示文件里的条数；导入后显示新增、跳过、加了「（导入）」标记的各几条。

## 8. 以后改格式

- 格式版本或派生算法要变，就加新的编号，旧编号照旧能导入。
- 新的明文字段尽量做成可选的，这样不用升 `format`。
